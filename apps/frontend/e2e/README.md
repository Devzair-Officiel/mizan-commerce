# Audits navigateur (Playwright)

Scripts lancés **sans Node sur la machine** : service Docker Compose `e2e` (image officielle `mcr.microsoft.com/playwright`, profil `audit`, ne démarre pas avec la stack). Il cible le frontend du réseau compose (`http://frontend:3000`) et se connecte avec le **compte dédié aux audits** `e2e@example.com` (mot de passe `Mizan1234!`, créé par `seed_data`).

```bash
# Depuis la racine du dépôt, stack démarrée (docker compose up -d)
docker compose run --rm e2e                                   # tous les audits, 3 à la fois, en smoke, boutiques d'audit remises à zéro avant
docker compose run --rm e2e npm run audit -- sales scroll-lock   # une liste d'audits, en parallèle aussi
AUDIT_MATRIX=full docker compose run --rm e2e                 # les 8 configurations (avant une pull request)
AUDIT_JOBS=4 docker compose run --rm e2e                      # 4 audits à la fois (4 boutiques d'audit recréées)
docker compose run --rm e2e npm run audit:pages               # écrans principaux
docker compose run --rm e2e npm run audit:customer-form       # formulaire client
docker compose run --rm e2e npm run audit:customer-name       # nom complet des clients partout
docker compose run --rm e2e npm run audit:zakat               # zakat : erreurs notifiées, plus d'alert()
docker compose run --rm e2e npm run audit:products-list       # liste Articles et services
docker compose run --rm e2e npm run audit:product-form        # formulaire article
docker compose run --rm e2e npm run audit:product-formats     # formats dans le formulaire article (création, modification)
docker compose run --rm e2e npm run audit:product-photos      # photos d'articles au format carré
docker compose run --rm e2e npm run audit:stock               # stock : niveaux, mouvements, entrées, sorties
docker compose run --rm e2e npm run audit:reminders           # rappels : compteurs, terminer/annuler, reporter, relancer, attribution
docker compose run --rm e2e npm run audit:reminder-form       # formulaire de rappel : création, modification, cartes des fiches
docker compose run --rm e2e npm run audit:reminders-staff     # module Rappels d'un employé : sans, accordé depuis Équipe, attribution et badge
docker compose run --rm e2e npm run audit:reminder-timezone   # raccourcis et « Reporter » à l'heure de la boutique, appareil dans un autre fuseau
docker compose run --rm e2e npm run audit:order-numbers       # numéros de commande et de facture en arabe : isolés, lus de gauche à droite
docker compose run --rm e2e npm run audit:whatsapp            # messages WhatsApp : envoi enregistré, historique des fiches
docker compose run --rm e2e npm run audit:message-templates   # modèles de messages : ton, aperçu, personnaliser/rétablir, variable inconnue, saisie pendant l'enregistrement
docker compose run --rm e2e npm run audit:sales               # bloc Ventes de l'accueil : trois périodes, bulle souris et clavier, période gardée
docker compose run --rm e2e npm run audit:activity-export     # export de l'activité d'un client : fenêtre, nombre de lignes, CSV téléchargé
docker compose run --rm e2e npm run audit:invoices            # factures : liste serveur, filtres, détail figé, PDF et annulation
docker compose run --rm e2e npm run audit:scroll-lock         # fenêtres et menus enchaînés : la page défile toujours
docker compose run --rm e2e npm run audit:header-bands        # bandes d'en-tête teintées : fond muted, contrastes ≥ 4,5:1
docker compose run --rm e2e npm run audit:show-more           # listes longues des fiches : 5 éléments puis « Voir plus »
docker compose run --rm e2e npm run audit:stock-entry-plan    # entrée de stock en Solo : carte Boutique sur l'onglet facture, aucune requête OCR
docker compose run --rm e2e npm run audit:account-menu        # menu compte : badge d'abonnement (essai, Solo, essai terminé) et raccourci clair/sombre du header
docker compose run --rm e2e npm run audit:sidebar             # sidebar desktop : déployée sans défilement à 1440×900, survol décalé (RTL), « ⋯ » du pied, bouton de bord et Ctrl+B, rail, flyout (survol, clavier, RTL), préférence gardée sur le compte
docker compose run --rm e2e npm run audit:usage               # jauges d'usage en Découverte (fr clair 1440, ar sombre 360) : bandeau ambre puis rouge, « Nouvelle commande » ouvre la carte Solo, jauges de l'abonnement
docker compose run --rm -e ONLY=clients,articles e2e npm run audit:pages   # écrans choisis
docker compose run --rm --no-deps e2e npm run audit:stock     # sans remise à zéro : garde les données actuelles
docker compose exec backend python manage.py reset_audit_shop # remise à zéro seule, à la main
```

Code de sortie 0 = tout est conforme, 1 = au moins une vérification en échec (détaillée dans la sortie).

## Configurations et parallélisme

- `AUDIT_MATRIX` : `smoke` (par défaut) parcourt 1440px fr clair et 360px ar sombre ; `full` les 8 configurations (1440px et 360px × fr et ar × clair et sombre). Les audits qui ne changent ni de langue ni de thème (pages, numéros de commande, fuseau des rappels, rappels d'un employé) passent toujours aux deux tailles.
- `run-audits.mjs` (`npm run audit`) lance les audits demandés, `AUDIT_JOBS` à la fois (3 par défaut). Chaque audit en cours occupe un **emplacement** : son propre compte et sa propre boutique d'audit (`e2e@example.com`, `e2e2@example.com`, `e2e3@example.com`, avec leurs employées `e2eN-staff@example.com`), recréés par `reset_audit_shop --slots`. Deux audits ne touchent donc jamais aux mêmes données ; les comptes de démo partagés (Youssef, services) ne sont que lus.
- Sessions partagées entre les audits d'un lancement : la limite `auth` du backend (10 connexions par minute, toutes vues depuis le frontend) n'est pas atteinte.
- Sortie complète de chaque audit dans `results/<audit>.log` (ignoré par git) ; le lanceur n'affiche que les vérifications en échec et les durées.
- `npm run audit:<audit>` lance un audit seul, sans le lanceur, sur la boutique `e2e@example.com`.

## Compte et boutique d'audit

- `e2e@example.com` possède sa propre boutique, « Boutique Audit » (et `e2e2@`, `e2e3@`… « Boutique Audit 2 », « 3 »…, identiques, pour les audits lancés en parallèle) (France, EUR, articles et services, vente sur place, Boutique), avec quelques articles, services, clients et commandes (`apps/backend/apps/core/management/commands/_seed_e2e.py`). `e2e-invoices@example.com` (« Boutique Audit Factures », identique) est réservé à `audit-invoices`, hors emplacements : il compte exactement ses factures, que celles d'`invoice-settings` et d'`order-numbers` ne doivent pas grossir. « Nadia Relance » a une commande impayée : l'audit y teste « Relancer ».
- Les audits créent tout ce dont ils ont besoin **dans cette boutique**, jamais dans celles des autres comptes de démo ; l'audit du formulaire client vérifie à la fin qu'aucun client de test n'existe dans la boutique de Youssef.
- Ils restent **relançables plusieurs fois de suite** : ce qu'ils créent est archivé ou supprimé à la fin, et ce qu'ils modifient est remis en place au début.
- **Données de départ connues** : `docker compose run --rm e2e` lance d'abord le service `e2e-reset` (`python manage.py reset_audit_shop`, profil `audit`), qui supprime les boutiques dont un compte d'audit est propriétaire puis recrée une « Boutique Audit » par emplacement et ses données de départ, comme `seed_data`. Les autres boutiques ne sont pas touchées. Mêmes gardes que `seed_data` : `DEBUG` ou `ALLOW_SEED=1`. Un audit lancé seul repart aussi de ces données ; `--no-deps` les garde telles quelles (le frontend doit alors déjà tourner).
- `seed_data --reset` supprime aussi la boutique et la recrée, avec celles des autres comptes de démo (comptes `@example.*` uniquement).
- `openSession(browser, viewport, { email })` permet, si besoin, de se connecter avec un autre compte de démo.

## Contenu

- `lib/watch.mjs` — **console surveillée** : toute erreur ou tout avertissement en console et toute exception non rattrapée font échouer l'audit ; **éléments interactifs imbriqués** (bouton dans un lien, etc.).
- `lib/scroll.mjs` — **défilement contrôlé après chaque interaction** de chaque audit (clic, saisie, touche, navigation), branché par `openSession` : une fois fenêtres et menus refermés, la page défile à la molette et rien ne reste bloquant sur html, body et `main` (overflow, pointer-events, inert, aria-hidden, verrou de Base UI). Un blocage est compté avec les problèmes de console de l'étape.
- `lib/wait.mjs` — **attentes sur un état précis** (pas de `waitForTimeout` dans les audits) : animations terminées (`animationsDone`), prochain changement du DOM (`domChange`), focus arrivé (`focusReached`), boîte de dialogue du navigateur refusée (`dismissedDialog`).
- `lib/session.mjs` — configurations (`AUDIT_MATRIX`, `inMatrix`), navigateur, connexion (compte de l'emplacement, `e2e@example.com` par défaut ; une connexion par taille d'écran, ou session partagée par le lanceur : la limite `auth` du backend reste basse), langue (`NEXT_LOCALE`) et thème (réponse `/auth/me/` réécrite, préférences du compte intactes).
- `lib/messages.mjs` — textes attendus lus dans `../messages/*.json` (montés en lecture seule) : `msg` (texte brut) et `fmt` (paramètres ICU appliqués : `{var}`, `select`, `plural` avec `=n` et `#`).
- `lib/products.mjs` — appels du backend par le proxy (`api`, `allResults`), création d'un article de test, désactivation ou suppression en fin d'audit.
- `lib/form.mjs` — gabarit de formulaire v3 : carte repliable (mobile) ouverte, refermée ou remplie avec son résumé, disposition vérifiée (`layoutOk` : deux colonnes et rien à déplier sur desktop, cartes empilées dans l'ordre et facultatives repliées sur mobile).
- `lib/photos.mjs` — image de test très haute ou très large dessinée dans le navigateur, envoi par l'API, mesure des photos affichées (cadre carré, `object-cover`, fond `bg-muted`).
- `lib/invoice.mjs` — facture fournisseur de test (page HTML capturée en PNG, ou imprimée en PDF avec texte), envoyée ensuite à la vraie chaîne de lecture.
- `audit-pages.mjs` — écrans principaux à 1440px et 360px.
- `audit-customer-form.mjs` — gabarit de formulaire v3 sur le formulaire client, à 1440px et 360px, clair et sombre, français et arabe :

  - aperçu de l'identité (initiales et nom) mis à jour pendant la saisie ;
  - actions sous les colonnes, sans cadre, en fin de ligne ; « Annuler » demande confirmation si le formulaire est modifié ;

## Exceptions de la console surveillée

Seulement les messages de l'outillage de développement qui ne viennent pas de notre code (`[Fast Refresh]`, `[HMR]`, invitation React DevTools) et l'échec du WebSocket de rechargement à chaud dans l'**aperçu de la page publique** : l'iframe est en `sandbox` sans `allow-same-origin` (origine opaque), le serveur de dev refuse donc ses ressources de développement. C'est attendu en développement ; le sandbox ne doit pas être assoupli (voir `components/public-page-admin/PreviewCard.tsx`).

## Notes

- Version de Playwright figée dans `package.json` ; elle doit correspondre au tag de l'image dans `docker-compose.yml`.
- `next.config.ts` autorise l'hôte `frontend` en développement (`allowedDevOrigins`) et Chromium traite `http://frontend:3000` comme origine sûre (`crypto.randomUUID`, utilisé par la nouvelle commande). Ce drapeau n'est lu que par le canal `chromium` (nouveau mode sans interface) : le « headless shell » par défaut l'ignore.
- Les limites de requêtes `user` et `anon` sont relevées dans `config/settings/local.py` pour que les audits ne les atteignent pas.

- `audit-invoice-settings.mjs` — Paramètres › Factures : gabarit v3 desktop/mobile, trois modes de couleur et contraste, TVA, virement et masquage des coordonnées bancaires, options au clavier, enregistrement, persistance, vrai téléchargement PDF, console propre. Inclus dans `npm run audit` ; ciblage : `docker compose run --rm e2e npm run audit -- invoice-settings`.
