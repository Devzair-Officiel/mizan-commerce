# Audits navigateur (Playwright)

Scripts lancés **sans Node sur la machine** : service Docker Compose `e2e` (image officielle `mcr.microsoft.com/playwright`, profil `audit`, ne démarre pas avec la stack). Il cible le frontend du réseau compose (`http://frontend:3000`) et se connecte avec le **compte dédié aux audits** `e2e@example.com` (mot de passe `Mizan1234!`, créé par `seed_data`).

```bash
# Depuis la racine du dépôt, stack démarrée (docker compose up -d)
docker compose run --rm e2e                                   # tous les audits, un à la fois, en smoke, boutiques d'audit remises à zéro avant
docker compose run --rm e2e npm run audit -- sales scroll-lock   # une liste d'audits
AUDIT_MATRIX=full docker compose run --rm e2e                 # les 8 configurations (préparation d'une pull request ou demande explicite)
AUDIT_JOBS=2 docker compose run --rm e2e                      # 2 audits à la fois (2 boutiques d'audit recréées), après validation des mesures mémoire
docker compose run --rm e2e npm run audit:pages               # écrans principaux
docker compose run --rm e2e npm run audit:customer-form       # formulaire client
docker compose run --rm e2e npm run audit:customer-name       # nom complet des clients partout
docker compose run --rm e2e npm run audit:zakat               # zakat : accueil, réglages, assistant (choix, seuil, conflit, année prise), justificatif PDF, fiches Fondement au clavier

docker compose run --rm -e ONLY=clients,articles e2e npm run audit:pages   # écrans choisis
docker compose run --rm --no-deps e2e npm run audit:stock     # sans remise à zéro : garde les données actuelles
docker compose exec backend python manage.py reset_audit_shop # remise à zéro seule, à la main
```

Code de sortie 0 = tout est conforme, 1 = au moins une vérification en échec (détaillée dans la sortie).

## Configurations et parallélisme

- `AUDIT_MATRIX` : `smoke` (par défaut) parcourt 1440px fr clair et 360px ar sombre ; `full` les 8 configurations (1440px et 360px × fr et ar × clair et sombre). Les audits qui ne changent ni de langue ni de thème (pages, numéros de commande, fuseau des rappels, rappels d'un employé) passent toujours aux deux tailles.
- `run-audits.mjs` (`npm run audit`) lance les audits demandés, `AUDIT_JOBS` à la fois (1 par défaut, pour la mémoire de la machine ; à passer en préfixe de `docker compose run`, que `e2e-reset` lit aussi). Chaque audit en cours occupe un **emplacement** : son propre compte et sa propre boutique d'audit (`e2e@example.com`, `e2e2@example.com`, `e2e3@example.com`, avec leurs employées `e2eN-staff@example.com`), recréés par `reset_audit_shop --slots`. Deux audits ne touchent donc jamais aux mêmes données ; les comptes de démo partagés (Youssef, services) ne sont que lus.
- Mémoire : conteneur limité à 3 Go sans swap (`AUDIT_MEM_LIMIT`, `AUDIT_MEMSWAP_LIMIT`) : au-delà, Chromium s'arrête dans le conteneur au lieu de saturer la machine. Chaque audit ferme son navigateur dans un `finally` ; après chaque audit, le lanceur vérifie qu'aucun processus Chromium ne reste (sinon échec, processus arrêtés). `infra/scripts/mem-check.sh run <commande>` relève la mémoire pendant un lancement.
- Sessions partagées entre les audits d'un lancement : la limite `auth` du backend (10 connexions par minute, toutes vues depuis le frontend) n'est pas atteinte.
- Sortie complète de chaque audit dans `results/<audit>.log` (ignoré par git) ; le lanceur n'affiche que les vérifications en échec et les durées.
- `npm run audit:<audit>` lance un audit seul, sans le lanceur, sur la boutique `e2e@example.com`.

## Compte et boutique d'audit

- `e2e@example.com` possède sa propre boutique, « Boutique Audit » (et `e2e2@`, `e2e3@`… « Boutique Audit 2 », « 3 »…, identiques, pour les audits lancés en parallèle) (France, EUR, articles et services, vente sur place, Boutique), avec quelques articles, services, clients et commandes (`apps/backend/apps/core/management/commands/_seed_e2e.py`). `e2e-invoices@example.com` (« Boutique Audit Factures », identique) est réservé à `audit-invoices`, hors emplacements : il compte exactement ses factures, que celles d'`invoice-settings` et d'`order-numbers` ne doivent pas grossir. `e2e-invoice-editor@example.com` (« Boutique Audit Éditeur », identique) est réservé de même à `audit-invoice-editor` : il part de deux brouillons de facture, un complet (Marc Dupuis, ligne du catalogue, ligne libre) et un vide, qui ne doivent pas entrer dans les comptes d'`audit-invoices`. « Nadia Relance » a une commande impayée : l'audit y teste « Relancer ».
- Les audits créent tout ce dont ils ont besoin **dans cette boutique**, jamais dans celles des autres comptes de démo ; l'audit du formulaire client vérifie à la fin qu'aucun client de test n'existe dans la boutique de Youssef.
- Ils restent **relançables plusieurs fois de suite** : ce qu'ils créent est archivé ou supprimé à la fin, et ce qu'ils modifient est remis en place au début.
- **Données de départ connues** : `docker compose run --rm e2e` lance d'abord le service `e2e-reset` (`python manage.py reset_audit_shop`, profil `audit`), qui supprime les boutiques dont un compte d'audit est propriétaire puis recrée une « Boutique Audit » par emplacement et ses données de départ, comme `seed_data`. Les autres boutiques ne sont pas touchées. Mêmes gardes que `seed_data` : `DEBUG` ou `ALLOW_SEED=1`. Un audit lancé seul repart aussi de ces données ; `--no-deps` les garde telles quelles (le frontend doit alors déjà tourner).
- `seed_data --reset` supprime aussi la boutique et la recrée, avec celles des autres comptes de démo (comptes `@example.*` uniquement).
- `openSession(browser, viewport, { email })` permet, si besoin, de se connecter avec un autre compte de démo.

## Contenu

- `lib/watch.mjs` — **console surveillée** : toute erreur ou tout avertissement en console et toute exception non rattrapée font échouer l'audit ; **éléments interactifs imbriqués** (bouton dans un lien, etc.).
- `lib/scroll.mjs` — **défilement contrôlé après chaque interaction** de chaque audit (clic, saisie, touche, navigation), branché par `openSession` : une fois fenêtres et menus refermés, la page défile à la molette et rien ne reste bloquant sur html, body et `main` (overflow, pointer-events, inert, aria-hidden, verrou de Base UI). Un blocage est compté avec les problèmes de console de l'étape.
- `lib/wait.mjs` — **attentes sur un état précis** (pas de `waitForTimeout` dans les audits) : animations terminées (`animationsDone`), prochain changement du DOM (`domChange`), focus arrivé (`focusReached`), boîte de dialogue du navigateur refusée (`dismissedDialog`).
- `lib/session.mjs` — configurations (`AUDIT_MATRIX`, `inMatrix`), navigateur, connexion (compte de l'emplacement, `e2e@example.com` par défaut ; une connexion par taille d'écran, ou session partagée par le lanceur : la limite `auth` du backend reste basse), langue (`NEXT_LOCALE`) et thème (réponse `/auth/me/` réécrite, préférences du compte intactes).
- `lib/messages.mjs` — textes attendus lus dans `../messages/*.json` (montés en lecture seule) : `msg` (texte brut) et `fmt` (paramètres ICU appliqués : `{var}`, `select`, `plural` avec `=n` et `#`).
- `lib/products.mjs` — appels du backend par le proxy (`api`, `allResults`), création d'un article de test, désactivation ou suppression en fin d'audit.
- `lib/form.mjs` — gabarit de formulaire v3 : carte repliable (mobile) ouverte, refermée ou remplie avec son résumé, disposition vérifiée (`layoutOk` : deux colonnes et rien à déplier sur desktop, cartes empilées dans l'ordre et facultatives repliées sur mobile).
- `lib/photos.mjs` — image de test très haute ou très large dessinée dans le navigateur, envoi par l'API, mesure des photos affichées (cadre carré, `object-cover`, fond `bg-muted`).
- `lib/invoice.mjs` — facture fournisseur de test (page HTML capturée en PNG, ou imprimée en PDF avec texte), envoyée ensuite à la vraie chaîne de lecture.
- `audit-pages.mjs` — écrans principaux à 1440px et 360px.

## Exceptions de la console surveillée

Seulement les messages de l'outillage de développement qui ne viennent pas de notre code (`[Fast Refresh]`, `[HMR]`, invitation React DevTools) et l'échec du WebSocket de rechargement à chaud dans l'**aperçu de la page publique** : l'iframe est en `sandbox` sans `allow-same-origin` (origine opaque), le serveur de dev refuse donc ses ressources de développement. C'est attendu en développement ; le sandbox ne doit pas être assoupli (voir `components/public-page-admin/PreviewCard.tsx`).
